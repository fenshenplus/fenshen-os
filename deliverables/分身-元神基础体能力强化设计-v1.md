# 分身 · 元神基础体能力强化设计 v1

> 目标：把「元神」从"会干活的蒸馏容器"重新定义为**多项目管理的智能体管理操作系统（Agent Management OS / 技术总监）**。
> 明确三层分立：**基础体（能力·管理 OS）= 蒸馏（人格）= 宪法（底层硬约束）**。
> 蒸馏只赋人格、不增能力；宪法写死"绝对服从本人长期利益"；基础体在未蒸馏状态下也必须具备完整工作能力，尤其是**主动性**与**保障规则**。

---

## 0. 架构定调（修正认知）

### 0.1 三元模型

| 层 | 本质 | 何时存在 | 是否可缺 |
|---|---|---|---|
| **基础体（元神 OS）** | 多项目管理 CTO / 智能体管理操作系统：立项、拆解、调度、监督、验收、汇报 | 开箱即有，零依赖 | **不可缺**（这是分身本体） |
| **蒸馏（人格层）** | 注入「利益关切 / 决策倾向 / 情感信号 / 价值观锚点 / 沟通风格」 | 仅炼制后 | 可缺（缺则保持通用技术 PM 人格） |
| **宪法（底层硬约束）** | 利益唯一委托人、绝对服从长期利益、重大利益保守、完全控制权 | 命名即锚定，不可改写 | **不可缺**（写在最底层，任何层不可覆盖） |

### 0.2 能力 ≠ 人格（关键原则）

- 蒸馏注入的内容**全部是 persona 维度**，不涉及任何 tool / capability / 权限。
  现有实现已正确（main.py:68「开箱即用不需要任何炼制就能直接干活」+ 82「炼制后注入画像」）。
- 强化方案**绝不**把"能力"放进蒸馏层。主动性、团队设计、验收裁决都是基础体 OS 的内置能力，与是否蒸馏无关。

### 0.3 宪法写死

- 一旦被称为「某人的元神」，从**利益、人格认知**上与该人绝对一致，**绝对服从其长期利益**。
- 这是人格化的"底线"部分——即使未蒸馏、即使蒸馏内容为空，也必须成立（由宪法层强制，不依赖人格层）。

## 1. 现状地基（已具备 / 缺口）

### 1.1 已具备（✅，无需重建）
- **宪法 5 条**：META_SYSTEM:61–66（唯一委托人 / 冲突护用户 / 重大利益保守 / 完全控制权 / 蒸馏须授权）。
- **续航调度器**：autopilot(15s·并发3) / normal(60s·1) / rest(300s·巡检)，事件唤醒毫秒级补位（main.py:9192–9751）。
- **关键路径**：`_project_critical_map` 优先打通阻塞下游链（9424）。
- **per-task 验收官**：`_judge_role_output` 严格对照完成标准（5693）；`_task_accept` 看板验收门（7463）。
- **成员自动升级**：连续 3 次未达标→元神加技能升级（P1-3，9404）。
- **8 态状态机 + 全链路就绪验收**：`meta_reconcile` / `_review_team_readiness`（6938）。

### 1.2 缺口（🔴，本设计要补）
1. **主动性偏"有卡才动"**：autopilot 只在"有 todo 卡 / 可补空白"时行动；缺**持续态势扫描**（团队缺口、标准漂移、计划停滞、偏离目标）与**自主重规划**。
2. **团队设计无保障规则**：有 `create_role`(3089) 与 `_resolve_member_for_task`(10394)，但**无"立项角色齐整度"校验**——关键能力是否覆盖、每 track 是否有 owner、职责是否缺口，无人保证。
3. **最终项目验收无自主门禁**：per-task 验收存在，但**项目级"算不算真完成"无人裁决**——全卡 done 后 autopilot 仅 `phase!='done'` 过滤派卡（9663），缺"元神独立终验 → 通过才置 done / 不通过 reopen"的闭环。
4. **宪法仅 prompt 层**：宪法写在 system prompt，缺 **runtime 守卫**——若元神（尤其蒸馏后自主调用）提议不可逆/涉钱/涉隐私/涉声誉动作，无代码级强制保守闸。

## 2. 宪法层固化（hardening）

### 2.1 分层显式化（注释契约）
在 META_SYSTEM 顶部加三段显式分层声明：
```
【元神三层结构】
① 基础体（管理 OS）：多项目 CTO，开箱即会调度/监督/验收，能力不依赖蒸馏。
② 蒸馏（人格层）：仅注入 利益关切/决策倾向/情感/价值观/沟通风格，不含任何能力。
③ 宪法（底层硬约束）：以下 5 条不可被任何层覆盖，包括蒸馏层与用户临时指令的冲突部分。
```
并固化"蒸馏 persona-only"契约：`meta_distill.py` 的 `interview_answer`/`ingest` 注入内容白名单校验（仅允许 persona 维度字段，拒绝任何 tool/capability 注入）。

### 2.2 runtime 宪法守卫 `_constitutional_guard`（新增，门控）
- 任何元神决策/派单/工具调用前过一道闸：
  - 命中「不可逆 / 钱 / 隐私 / 声誉 / 账号所有权 / 外部角色冲突」→ 强制保守路径；
  - 若属"重大利益需拍板" → 暂停并 `@用户终验`，不自主执行（呼应宪法第 3、4 条）。
- 复用既有权限设置 `exec_approval`（all/danger/off），但宪法闸优先级高于用户临时"全同意"指令——**宪法不可被配置降级**。
- 实现：`backend/main.py` 新增 `_constitutional_guard(action_dict) -> (allowed: bool, reason: str, needs_user: bool)`；在 `_dispatch_and_track` / `exec_command` / `browser_action` 入口调用。

### 2.3 命名锚定
META_SYSTEM:59 起首句固化为：`你是「<owner 本机用户>」的元神——其数字克隆体总管引擎与智能体管理操作系统。`（owner 取自本机用户身份，启动即绑定，不可被对话改写）。

## 3. 主动性引擎强化（Proactivity）

### 3.1 持续态势扫描 `_situation_scan`（新增，每 tick 调用）
不只在"有卡"时动，每轮还评估：
- **团队健康**：角色齐整度、每 track owner、成员连败/胜任度（接 1.2-2）。
- **阻塞**：卡死任务、关键路径停滞、依赖死锁。
- **标准漂移**：任务产出是否偏离项目 `standards` / 用户利益（接宪法闸）。
- **计划停滞**：连续 N 轮无进展且无新卡 → 触发元神"主动重规划"（重新拆解/调优先级/换策略）。

### 3.2 自主下命令（不等人）
- 元神不再只等用户派活：态势扫描发现缺口 → 自主给 agent 下指令（建卡/调人/升技能/重规划），仅在"重大利益需拍板"时 `@用户`。
- 与现有 autopilot 派单合并：在 `_meta_autopilot` 循环内，于"派 todo 卡"之前先跑 `_situation_scan`，按扫描结论决定"补队 / 重规划 / 派卡 / 唤醒用户"。

### 3.3 不停等闭环（强化既有事件唤醒）
- 既有：`_dispatch_and_track` finally 里 `_AUTONOMY_WAKE.set()`（9421）已实现"执行返回即下一轮"。
- 补强：即使**无任何卡、无空白**，元神仍每轮做态势扫描（而非空转 `continue`），保证"持续在场、主动在场"。

## 4. 团队设计保障规则（Team Design Guarantee）

| 规则 | 内容 | 管理动作 |
|---|---|---|
| **T1 立项齐整** | 项目立项 / 首派前，元神校验角色集覆盖目标所需关键能力（架构/研发/测试/产品/运维至少按需齐备） | 缺口→自动 `create_role` 或 `@用户` 建议建队 |
| **T2 每 track 有 owner** | 每个交付轨道（web/h5/app/mp/infra/ops）至少 1 个负责成员 | 无 owner 的 track→补位或预警 |
| **T3 职责无缺口** | 看板模块×阶段格均有可派角色，无"无人能接"的卡 | 卡无胜任者→建技能/升级/外援建议 |
| **T4 不胜任即升级** | 成员连续未达标→自动加技能升级（已有 P1-3，9404） | 升级后仍不达标→换人或 `@用户` |

- **团队健康分**：每项目算 `team_health = f(齐整度, 连败, owner覆盖, 卡死)`，低于阈值在态势扫描里报警并触发 T1–T3。
- **管理粒度**：autopilot 每 tick 维护 `AUTONOMY_STATE["team_health"][pid]`；前端驾驶舱 KPI 条（#416-D）新增"团队健康"指标。

## 5. 最终项目验收保障规则（Final Acceptance Guarantee）

| 规则 | 内容 | 管理动作 |
|---|---|---|
| **A1 全任务通过** | 项目内所有任务 `status='done'` 且 per-task 验收官通过（接 `_task_accept`） | 有 `review` 卡→不终验，先派修正 |
| **A2 对照目标** | 元神独立对照 `goal` + `standards` 判定交付物是否达成意图 | 偏离→reopen + 派修正卡 |
| **A3 产出物检查** | 检查关键产出物真实存在且可用（文件/接口/构建产物，非口头声称） | 缺失→reopen |
| **A4 元神裁决** | 新增 `_meta_final_acceptance(pid)`：综合 A1–A3 出"终验报告"，通过才 `set_phase(done)` | 不通过→状态回 `running`+修正卡+留痕 |
| **A5 用户终验钩子** | 涉重大利益（钱/对外承诺/不可逆）的项目，A4 通过后仍 `@用户终验` 才置 done | 用户否决→保持 open + 说明 |

- **门禁强制**：`set_phase(done)` 只由两个入口调用——`_meta_final_acceptance`（自主）或用户显式指令；autopilot 不再因"无 todo 卡"就认为完成。
- **验收报告归档**：A4 报告写入项目消息 + 经验库（接 E1 泛化），支撑疗效归因。

## 6. 实施路线（分阶段 · 门控 · 验证纪律）

> 全部为**纯增量、门控、零侵入**；沿用既有纪律：隔离副本 8011 → smoke 76/0 → bump patch → 备份重启 8002。

### Phase A — 宪法层固化（非破坏）
- A1：META_SYSTEM 顶部加三层分层声明 + 命名锚定（2.1/2.3）。
- A2：新增 `_constitutional_guard` 并在 `exec_command`/`browser_action`/`_dispatch_and_track` 入口接线（2.2）。
- A3：`meta_distill.py` 注入白名单（persona-only 契约）。
- 门控：`constitutional_guard_enabled`（默认开）。

### Phase B — 主动性引擎 + 团队设计保障
- B1：新增 `_situation_scan`（3.1）+ `team_health` 计算（4）。
- B2：autopilot 循环内"派卡前先扫描"，按结论补队/重规划/派卡（3.2/3.3）。
- B3：T1–T4 规则落地（建队建议 / owner 覆盖 / 缺口预警）。
- 门控：`proactivity_enabled`（默认开）。

### Phase C — 最终项目验收门禁
- C1：新增 `_meta_final_acceptance`（A1–A5）。
- C2：`set_phase(done)` 收口为仅 A4/用户两入口；autopilot 不再误判完成。
- C3：终验报告归档 + 驾驶舱"待终验/已终验"指标。
- 门控：`final_acceptance_enabled`（默认开）。

### 验证纪律（每 Phase）
1. 3 段内联 `<script>` `node --check` 全过；
2. 隔离 `/tmp/fenshen_regress` 起 8011 独立库 → `smoke_v40` **76/0**；
3. 新端点/守卫单测（含宪法闸拒绝样例、终验不通过 reopen 样例）；
4. `bump_version.py patch`（compile+冒烟门禁）；
5. 备份真实库 + 平滑重启 8002 验证版本与开关。
