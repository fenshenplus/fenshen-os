# 分身 · 群聊 token 档位与上下文调度设计（v1）

> 2026-08-19 ｜ 依据：`deliverables/分身-v6.4全面评测报告-v1.md` 实测（群聊 59 调用 / 198.9k tokens / 201s vs 单一 Agent 1 调用 / 1.1k tokens / 4.4s，准确性均 6/6）
> 用户意见：① 元神直接处理简单问答，只有复杂长程任务才建团队；② 全 agent 同模型 vs 不同模型的上下文调度；③ 设档位，按项目/按功能设施配置对应处理方式。
> 基线：SEMVER 0.64.13 / commit 99bb5ba / fix/v4.0-audit

---

## 一、token 开销归因（评测结论回顾）

| 环节 | 调用 | 实测占比 | 性质 |
|---|---|---|---|
| 元神调度（meta-dispatch） | 1 次 | input ~0.5-1.1k | 必要（决定做什么） |
| 角色执行（role-exec） | 每角色 1 次 | 2.5-4.5k/次，随轮次增长 | 必要（真正干活） |
| **验收官 LLM 判定** | 每 action 1 次 | ~1-2k/次 | **可降级**（无标准时可启发式） |
| **D8 写/测交叉** | 每代码任务 +1 tester | ~2-3k/次 | **可配置**（T1 可关） |
| **补做轮（元神重规划）** | 最多 5 轮 | 每轮重付 调度+执行+验收 | **可压缩**（标准写死/轻量档位直接过） |
| 上下文累积增长 | 单次 input 2.3k→4.5k | 群聊 6 条+历史回流 | **可压缩**（共享上下文池） |

**核心结论**：群聊模式多出的 token 主要是「质量体系」成本（验收+交叉+补做），对简单任务不划算。→ 档位化 = 按任务复杂度选择「要不要付这笔质量成本」。

## 二、档位体系（Tier 0-3）

### 判定流程：群聊消息 → 先路由分档 → 按档执行

```
用户群聊消息
   │
   ▼
[路由判定]（1 次轻量 LLM 调用，或关键词启发式直判）
   │
   ├── T0 即时直答：闲聊/问答/汇报/轻咨询 ──→ 元神单次直答（不建卡/不派单/不验收）
   ├── T1 单角色速办：单一明确小任务 ────────→ 规则路由单角色执行 + 启发式验收（≤3 次调用）
   ├── T2 团队协作：复杂/多角色/工程任务 ────→ 元神拆解 + 质量门 + LLM 验收 + D8 + 有界补做（现状）
   └── T3 长程自治：项目级持续交付 ────────────→ 续航调度器（现状 autopilot，不变）
```

### 各档 token 预算与质量保障

| 档 | 适用 | 调用次数 | 质量保障 | token 预估（单任务） |
|---|---|---|---|---|
| **T0 直答** | "今天进度如何""这个功能怎么做"类即时问答 | **1 次** | 元神人格+宪法约束天然在 | ~0.5-1.5k |
| **T1 速办** | "写个 hello.py""给按钮换个颜色"类单一明确小任务 | **1-3 次**（路由+执行，无标准即启发式验收） | 确定性质量门可选开（落盘可验证时） | ~3-8k |
| **T2 协作** | 跨角色/多文件/需测试的工程任务 | 5-59 次（现状） | 验收官+质量门+D8+补做（质量优先） | ~50-200k |
| **T3 自治** | 项目级无人值守推进 | 持续（现状） | 终验门禁 A1-A5 | 视任务量 |

> T1 与 T2 的关键分界：**任务是否明确、单一、可一次交付**。判断交给路由（LLM 或启发式），用户也可手动指定档位。

## 三、同模型 vs 不同模型的上下文调度（节约 token 的核心）

### 3.1 共享上下文池（Shared Context Pool）——两种模型策略共用

当前每角色执行时各自重新组装完整上下文（人格+项目目标+工作区+标准+纪律+爆炸半径+经验召回），N 个角色 = N 份重复组装。

**改造：上下文拆两段**

```
[共享段]（项目级，只构建 1 次，所有角色复用）
  项目名/目标/完成标准
  爆炸半径聚焦的模块切片（只投相关模块）
  群聊最近 6 条（压缩后）
  经验 top-k（同项目加权召回）
  执行纪律/质量约束/设计规范（全局常量）

[角色段]（按角色，仅此一段不同）
  soul / rule / eng_spec / done_criteria / 当前任务 detail
```

- 共享段构建 1 次，注入所有角色的 prompt 前缀；角色段拼在后面
- 效果：N 角色协作时，重复的"项目信息"只生成/编码一次，单次 input 从 4.5k → ~1.5-2.5k（共享段 1-1.5k + 角色段 0.5-1k）

### 3.2 同模型（全部 deepseek-v4-flash 等）——启用前缀缓存

- **DeepSeek 原生支持 context caching**（自动按 prompt 前缀命中缓存，命中部分费用 ≈0）
- 共享段作为**固定前缀**：同一项目内多个角色/多轮调用的共享段完全一致 → 全部命中缓存
- 补做轮/验收判定也复用同一共享段前缀 → 多轮补做的重复 token 成本大幅下降
- 实现：保证共享段文本**逐字符稳定**（同项目、同 blast scope、同消息窗口内不变）

### 3.3 不同模型（元神 deepseek / 前端 openai / 测试 claude...）——共享快照降重复

- 各模型 tokenizer 独立，无法共享编码缓存；但**快照内容一致**：共享段仍只组装一次（源码级），发给各模型时按各自 tokenizer 编码
- 优化点：① 共享段严格控制长度（压缩摘要而非原始数据）；② 群聊 6 条上限 + 经验 top-k 截断；③ 每角色仅拉自己的角色段
- 收益：虽然多模型无法命中缓存，但**单次调用 input 变小**（共享段压缩），且避免 N 角色各自拉全量项目数据（N×原始数据 → 1×快照）

### 3.4 调度差异总表

| 场景 | 上下文组装 | 缓存收益 | 主要省 token 手段 |
|---|---|---|---|
| 同模型 + T2 多角色 | 共享段 1 次 + 角色段 N 次 | **前缀缓存命中**（多轮/多角色共享段相同） | 缓存 + 快照压缩 |
| 同模型 + T1 单角色 | 共享段 1 次 | 缓存命中（若同项目后续任务复用） | 快照压缩 + 免验收 |
| 不同模型 + T2 | 共享快照 1 次源码组装，各模型独立编码 | 无跨模型缓存 | 快照压缩 + 群聊 6 条 + top-k 截断 |
| T0 直答 | 最小 system（元神人格+项目名+最近 2 条） | 无 | 根本不建上下文（最低开销） |

## 四、档位配置（按项目 / 按功能设施）

### 4.1 全局默认（settings 表，进 `_CODE_SETTING_KEYS`）

| 开关 | 默认 | 说明 |
|---|---|---|
| `chat_tier_enabled` | 1 | 档位体系总开关（关=现状 T2 一律走） |
| `chat_tier_default` | "auto" | auto / 0 / 1 / 2（auto=元神路由判定） |
| `tier0_quick_answer` | 1 | T0 直答开关 |
| `tier1_solo_exec` | 1 | T1 单角色速办开关 |
| `tier1_skip_llm_judge` | 1 | T1 无标准时跳过 LLM 验收（启发式） |
| `tier1_skip_xverify` | 1 | T1 跳过 D8 写测交叉 |
| `shared_context_pool` | 1 | 共享上下文池开关 |

### 4.2 项目级覆盖（projects.product_meta JSON）

```
product_meta.tier = "auto" | 0 | 1 | 2   （前端「项目设置」可改）
product_meta.tier_note = "轻量项目：闲聊+小任务即答，复杂任务才建队"
```

- 项目设置 UI 加「执行档位」下拉：自动 / 即时直答 / 单角色速办 / 团队协作
- 判定优先级：项目 tier > 全局 chat_tier_default

### 4.3 功能设施级

| 设施 | 建议档位 | 理由 |
|---|---|---|
| 群聊即时问答/闲聊 | 强制 T0 | 高频低价值，必须最省 |
| 群聊内小任务（单一角色可完成） | 默认 T1，项目可调 T2 | 平衡速度与质量 |
| 看板任务/续航派单 | 强制 T2/T3 | 工程交付需质量门 |
| 蒸馏/记忆/技能（后台） | 维持现状（各自独立开关） | 不与群聊档位耦合 |

## 五、路由判定实现（关键：把"分档"做进现有调度调用）

**方案 A（推荐，省一次调用）**：调度 prompt 输出加 `tier` 字段——

```
{"tier": 0|1|2, "reply": "...", "actions": [...]}
```

- tier=0：元神调度这次调用即最终回复（已存在 actions=[] 逻辑，只是显式化 + 走轻量 system）
- tier=1：只取 `actions[0]`，跳过 D8/LLM 验收/补做，单角色执行后启发式验收即收尾
- tier=2：现状完整链路
- **token 收益**：调度 1 次调用同时完成"分档+决策"，不额外增加调用

**方案 B（关键词启发式预判）**：正则匹配（"？/吗/呢/怎么"→T0；"写/做/改/创建"→T1/T2）先分流，T0 直接走轻量直答（省掉完整调度 prompt），不确定再走方案 A。
→ 建议 A+B 结合：先启发式预判 T0/T1（快、省），拿不准的进 A。

## 六、实施路线（门控、零侵入、延续隔离测试纪律）

| 步骤 | 内容 | 验证 |
|---|---|---|
| **P0** | 调度 prompt 加 `tier` 字段 + T0 直答分支（轻量 system，跳过建卡/派单/验收）+ 启发式预判 | 隔离 8011：T0 问答 =1 次调用；T2 不变 |
| **P1** | T1 单角色速办（路由→单角色→启发式验收，skip D8/LLM judge）+ 项目级 product_meta.tier | 隔离：T1 小任务 ≤3 次调用，产出正确 |
| **P2** | 共享上下文池（共享段/角色段拆分 + 同模型前缀缓存）+ 项目设置 UI 档位下拉 + 驾驶舱 token 三段显性化 | 隔离：T2 多角色 input 均值下降；smoke 76/0 无回归 |
| **收口** | bump 版本、备份、重启、写记忆 | 全套纪律 |

**验收口径**
- T0：即时问答响应 = **1 次 LLM 调用**，无任务卡产生
- T1：单一小任务 = **≤3 次调用**（路由+执行+可选启发式），产出正确
- T2：复杂任务质量不降（6/6 准确性保持），共享池后单次 input 均值下降 ≥30%
- 简单任务综合 token 对比评测前（198.9k）**预计降 1-2 个数量级**
- smoke_v40 76/0 全绿、无回归

## 七、风险与边界

- **T0 误判**：把该干的活当问答跳过 → 路由提示词强调"涉及执行/产出/修改的指令必须升档"，且用户可手动指定档位兜底
- **T1 质量**：跳过硬验收的小任务若出错 → 启发式验收至少拦空产出/失败标记；复杂任务自然升 T2
- **共享段稳定性**：同项目消息窗口内必须逐字符稳定才能命中缓存 → 实现时锁定快照版本号，变更即重建
- **兼容**：所有新开关默认开但保留关闭路径；旧行为（无 tier 字段）向后兼容
