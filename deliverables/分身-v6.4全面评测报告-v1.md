## 第一部分 整体评测：元神模式 vs 现有 Agent

### 1.1 产品定位对照

| 维度 | 元神模式（分身） | 现有单 Agent（ChatGPT / Claude / Manus / CodeBuddy 等） |
|---|---|---|
| 组织形态 | **群聊形态的 AI 团队总管**：每项目=一个群聊，元神调度多个角色成员 | 单人助手：一个 AI 全程包办 |
| 单元模型 | 项目 = 群聊房间；角色成员有独立人格（soul/rule/eng_spec） | 对话 = 一个上下文窗口 |
| 工作方式 | 元神拆解 → 专才执行 → 验收官判定 → 看板留痕 | 单上下文内自我拆解、自我执行、自我验收 |
| 多项目 | 原生多项目：项目矩阵看板 + 独立群聊 + 续航调度器轮巡 | 靠手动切换会话/项目，无跨项目调度 |
| 主动性 | 续航调度器 autopilot/normal/rest 三模式 + 停滞预警 + 自动补队 + 最终验收门禁（0.64.13） | 完成任务即停，等待用户指令 |

### 1.2 易用性评测（元神模式优势点）

1. **多项目群聊=零学习成本入口**：每个项目一个房间（`renderRooms` frontend/index.html:1471-1494），用户在群聊里用自然语言发指令即可驱动整条交付链；任务自动落进看板 `module×stage` 格子（`_resolve_dispatch_module` main.py:7420-7441），群聊消息带 `📌 看板` 跳转（index.html:1561），双向可追溯。
2. **无需理解"角色/任务/状态"概念**：元神承担 PM 职责——分析指令、输出 JSON 调度计划（`_execute_project_chat` main.py:5954，`dispatch_sys` 6013-6028），用户只描述"要什么"。
3. **续航不等待**：`autopilot`(15s·并发3)/`normal`(60s·并发1)/`rest`(300s·巡检)（main.py:9251-9255），事件唤醒 `_AUTONOMY_WAKE`（9286），任务完成自动推进下一卡。
4. **主动性闭环（0.64.13 本轮强化）**：`_team_health` 按模块 owner_role 实时算缺岗（9685-9702）→ `_ensure_team_for_project` 自动补建标准成员（9705-9729）→ `_situation_scan` 检测 doing 超时/todo 停滞并发预警；`_meta_final_acceptance`（A1-A5）项目全卡完成自动终验、无标准主动暂缓请用户、缺验收点自动 reopen 补修正卡。
5. **引导四件套（0.64.10）**：IN_APP_GUIDE / 空状态 / 帮助中心 / 首用向导 / 分步导览，新用户上手路径完整。

### 1.3 能力评测（元神模式优势点）

1. **专才分工而非全才包办**：`roles` 表（通用职责：架构师/后端/前端/测试/SRE，main.py:724-726、1179-1188）与 `agent_members`（项目级人格：soul/rule/eng_spec/model_cfg，1128-1151）两层；`_seed_default_roster` 建项目即种 5 名基础成员（2635-2659）。
2. **质量体系比单 Agent 更硬**：
   - 验收官 `_judge_role_output`（5723-5761）：优先任务 done_criteria → 项目 standards，LLM 判定 pass/fail；
   - 确定性质量门 `_code_verify_enabled`（6272-6286）：角色产出可落盘验证、可跑测试、可自动修复（max_fix 轮）；
   - 交叉验证 D8：派单自动追加 tester 角色验证；
   - 代码护栏 D10 / 宪法守卫（0.64.13）：硬编码密钥、危险命令、`git push --force` 等宪法级操作一律真人确认。
3. **记忆与进化**：experiences 5 维权重（relevance/recency/frequency/explicit_feedback/trust_score，791-813）+ 同项目加权召回（`_recall_experiences` 8297-8334）+ 群聊自动蒸馏（`_auto_distill_project_chat` 8613-8652）+ 磨压缩 + 疗效归因；成员失败连败≥3 自动升级（`_auto_upgrade_member` 10602-10680）。
4. **多模型降级链**：角色自有 Key → 全库其他角色 Key 按 `FALLBACK_ORDER` 顶上 → Ollama → DeepSeek secret（`_available_providers` 1472-1525），单点模型故障不影响交付。

### 1.4 效率评测（含实测数据，见第三部分模块三/四）

- 群聊模式 vs 单一 Agent 的 **token 开销差异**、**耗时差异**、**准确性差异**：见 3.3 实测表。

### 1.5 劣势与代价（元神模式）

## 第二部分 分模块评测

### 模块一：群聊模式——"有效群聊"是如何实现的

#### 1.1 角色系统两层结构
- **`roles` 表**（main.py:724-726）：`id/name/mandate/skills/gate`，通用职责元数据，种子 5 角色（1179-1188）。
- **`agent_members` 表**（1128-1151）：项目级人格——`soul`（角色定位）/`rule`（安全红线）/`eng_spec`（工程规范）/`model_cfg`（模型配置）/`work_hours`（作息）/`experience`/`level`/`evo_tree`（进化树）。`_seed_default_roster` 建项目即种 5 名基础成员（2635-2659），续航期按缺口补队（9705-9729）。

#### 1.2 群聊驱动链路（一次"有效群聊"的完整生命周期）
1. **用户发消息** → 落库 messages（kind=`self`，main.py:5979-5982）；
2. **元神分析**：`_compute_blast_radius` 先算爆炸半径（5885-5926），`_scoped_project_context` 生成聚焦切片（5929-5951），只把相关模块/任务投给元神（避免全项目广播）；群聊最近 6 条注入（5997-6000）；
3. **元神输出 JSON 调度计划**（`dispatch_sys` 6013-6028）：`{"reply": ..., "actions": [{"role", "task_name", "detail", "done_criteria", "plan"}]}`，闲聊/提问则 actions=[]（只回复不派单）；
4. **逐个角色执行**（`_run_one` 6104-6340）：建卡（或复用预存卡）→ doing 流转 → 组装该角色专属上下文 `role_sys_ctx`（角色系统+项目目标+工作区+done_criteria+执行纪律+代码语义+质量约束+设计规范+爆炸半径+经验召回，6184-6265）→ `_chat_with_tools` 执行（6278，ROLE_TOOLS 可写文件/跑命令，最多 6 轮工具循环）→ 产出写回群聊（kind=`agent`，sender=`分身 · {角色}`）；
5. **验收判定**：`_judge_role_output`（5723-5761）按 done_criteria→standards 判定 pass/fail；`verify_task`（7508-7562）达标→done+冻结基线版本（7547-7552），未达标→review+窄播受影响成员（7543-7562）；
6. **元神汇报**（6089-6093，kind=`meta`）→ 用户可见完整群聊。

#### 1.3 群聊有效性保障机制（区别于"玩具群聊"的关键）

| 机制 | 实现 | 作用 |
|---|---|---|
| 爆炸半径精准路由 | `_compute_blast_radius`+`blast_note`（6009-6012） | 上下文只投相关模块，防全项目广播导致的注意力稀释 |
| PAD 派单协议 | 单轮 ≤3 并行（`max_actions` 6006），串行执行 | 控制上下文膨胀与并发风险 |
| 验收官独立判定 | `_judge_role_output` 5723-5761 | 执行者与验收者分离，防自产自销 |
| 确定性质量门 | `_code_verify_enabled` 6272-6286 | 产出可落盘验证/可跑测试/可自动修复 |
| 熔断与升级 | `FAIL_BREAKER=5`（9248-9249）；`_auto_upgrade_member`（10602-10680） | 连败熔断防雪崩；成员能力自适应进化 |
| 成员间可见 | 产出全部进同一群聊（6300-6303），可互 @/私聊（`send_direct` 3225-3250） | 信息透明，可交叉校验 |
| 群聊↔看板联动 | task_id 反查 module×stage（index.html:3144-3160） | 聊天结论沉淀为可执行、可追踪的工作项 |

#### 1.4 前端群聊交互（frontend/index.html）
- 三栏布局 rooms|chat|split（492-576）；`renderChat`（1554-1571）：sys 居中、self 右气泡、agent/meta 左气泡、tag 显示 完成/进度/阻塞、`📌 看板` 跳转（1561）；
- 成员管理 `openMemberDrawer`（4612+）+ 1:1 私聊抽屉（4836-4890，direct_msgs 表）；
- 驾驶舱 `renderCockpitTeam`（4516-4533）展示成员头像/角色/等级/经验/当前任务。

### 模块二：多模型与上下文管理

#### 2.1 多模型现状
- **按 role 配置**：`model_configs` 表（738-744）→ `get_model_config`（1331-1337）按角色 id（backend/frontend/tester…）取模型；`_available_providers` 组装候选链（1472-1525）：①角色自有 Key 永远第一 ②全库其他角色 Key 按 `FALLBACK_ORDER`（121）顶上 ③Ollama 兜底 ④DeepSeek secret 文件兜底。
- **成员级 `model_cfg` 为元数据**（1128-1151 字段存在，但执行链读的是 `model_configs` 按 role 的配置；成员 model_cfg 仅在 auto-upgrade 10615-10670 更新 reason 标志）。
- **结论**：当前"每个成员用不同模型"的落地方式是**按角色维度**（不同角色可配不同模型/不同 Key），成员级模型差异化是预留字段、尚未接入执行链。

#### 2.2 上下文管理（隔离 vs 共享）
- **执行期上下文（隔离）**：每个角色任务独立组装 `role_sys_ctx`（角色人格+项目目标+工作区+标准+纪律+代码语义+质量约束+设计规范+爆炸半径+经验召回，6184-6265）；`_TOOL_TASK` contextvar（3776）在 `_run_one` 注入（6157），保证并发任务间上下文与 token 记账互不串扰。
- **群聊上下文（共享）**：项目级最近 6 条消息（5997-6000）作为对话背景；成员产出全量进群聊可见（6300-6303）。
- **长期记忆（共享+加权）**：experiences 表 5 维权重召回注入角色上下文（6249-6265），按 relevance/recency/frequency/反馈/信任度排序 top-k。
- **上下文压缩**：爆炸半径聚焦切片（P1-A）+ 群聊 6 条上限 + 会话归档（E6 `_maybe_compact_session`）+ 磨压缩（GRIND_SYSTEM 7786）。

## 第三部分 实测：群聊模式 vs 单一 Agent

### 3.1 实验设计（隔离副本 /tmp/fenshen_bench，同模型 deepseek-v4-flash）

- **同一任务**：`请实现一个 Python 函数 is_prime(n)：判断正整数 n 是否为质数，n<=1 返回 False。要求：①给出完整可运行的 Python 代码；②给出 3 个测试用例及其预期结果；③简述边界条件。`
- **场景 A（群聊模式）**：新建项目（含 1 模块 + 后端/测试成员）→ 走完整群聊链路 `_execute_project_chat`：元神调度（meta-dispatch）→ 角色执行（role-exec）→ 验收判定（judge）。全程通过 `project_id` 归因到 model_usage。
- **场景 B（单一 Agent）**：`_chat_with_tools("backend", tools=[])` 一次直答，同样的任务文本、同样的模型。
- **准确性验证**：从两场景产出中提取 is_prime 代码，对隐藏测试集 `[(0,F),(1,F),(2,T),(4,F),(97,T),(10^9+7,T)]` 实际执行计通过率。

### 3.2 结构性开销拆解（基于代码）

| 调用环节 | agent | 上下文构成 | 预估 input |
|---|---|---|---|
| 元神调度 | `__meta__` | 项目名/目标/角色枚举/爆炸半径切片/群聊 6 条/JSON 协议 | ~0.5-1k（历史均值 475） |
| 角色执行 | 具体角色 | 角色人格+项目目标+工作区+done_criteria+执行纪律+代码语义+质量约束+设计规范+爆炸半径+经验召回 | ~2-3k（历史均值 1.7-3k） |
| 验收判定 | 元神 | 产出+done_criteria/standards | ~1-2k |
| 单一 Agent 直答 | backend | 一个整合 prompt | ~1-3k |

→ 群聊模式**结构性多出**元神调度与验收判定两跳，且角色上下文携带人格/规范/爆炸半径等"管理开销"；单一 Agent 把这些全压进一个 prompt。

### 3.3 实测结果

> 同一任务、同一模型（deepseek-v4-flash），隔离副本实测（2026-08-19 10:36-10:40）。

| 指标 | 场景 A：群聊模式 | 场景 B：单一 Agent | 倍数 |
|---|---|---|---|
| LLM 调用次数 | **59**（元神 3 / 后端 17 / 测试 39） | **1** | **59×** |
| input tokens | 185,771 | 479 | 388× |
| output tokens | 13,167 | 611 | 22× |
| 总 tokens | **198,938** | **1,090** | **183×** |
| 端到端耗时 | 201.4s | 4.4s | 46× |
| 准确性（隐藏测试集 6 例） | **6/6 ✅** | **6/6 ✅** | 持平 |
| 任务卡/留痕 | 9 张卡（3 轮×动作），看板全程可追溯 | 无 | — |
| 交付物 | `is_prime.py` + `test_prime.py` + pytest 运行日志 + **行覆盖率 100% 报告**（真实文件落盘+证据链） | 文本回复（代码块+用例+边界说明，未落盘） | 群聊更完整 |

**调用构成拆解（场景 A，59 次）**：`__meta__` 3 次（元神调度 1.4k in / 补做轮重调度）；`backend` 17 次（角色执行+质量门验证+验收）；`tester` 39 次（质量门验证+验收判定占大头）。单次 input 2.5-4.5k，因每轮角色上下文都携带角色人格+项目目标+工作区+完成标准+爆炸半径+经验召回。

### 3.4 结果分析

**群聊模式开销的真实归因**（按消息回放逐条核对）：

1. **元神多轮拆解与补做（主因）**：任务被元神拆为"后端实现 + 测试写单测 + 覆盖率报告"多动作；第 1 轮测试工程师执行遇 `RemoteDisconnected` 网络瞬时故障（status=degraded 1 次）→ 验收官判定未达标 → 元神第 2 轮补做（重新拆 3 动作）→ 后端/测试产出"仅描述未附文件内容"再被验收官判未达标 → 元神第 3 轮补做（要求"直接产出可验证交付物"）→ 才通过。共 3 轮、9 张卡。
2. **质量门+验收官密集调用**：每动作执行后都触发确定性质量门（真实运行 pytest/覆盖率）与 LLM 验收判定（tester 39 次）；第 1 轮的 1 次网络故障被验收体系捕捉并放大为 2 轮补做。
3. **角色上下文叠加**：每轮补做都重新注入完整角色 system prompt + 累积群聊消息，input 从首轮 2.3k 涨到末轮 4.5k（群聊上下文 6 条 + 历史产出回流）。

**结论性解读**：
- **这是"质量体系的代价"，不是缺陷**：群聊模式宁可多花 10 倍 token 也要拿到"真实可验证的交付物"（文件落盘 + 测试日志 + 覆盖率证据 + 看板留痕）；单一 Agent 只给文本，答案正确性靠"模型自述"，无任何可验证物。
- **任务粒度失配是开销放大器**：is_prime 是单函数级任务，最适合单跳直答；群聊模式对其"杀鸡用牛刀"（拆解+验收+补做循环）。对多文件/跨角色/需真实验证的工程任务，相对开销会显著下降。
- **可优化方向**：①简单任务快路径（元神单跳直答，不建卡不派单）；②验收标准下沉（done_criteria 写死可机械判定的标准，减少"仅描述"误判）；③网络降级不触发补做轮（重试次数内直接重试而非重排）。

## 第四部分 结论与建议

### 4.1 结论

1. **元神模式的定位成立**：作为"多项目管理 + 团队调度 + 质量验收"的管理 OS，其易用性（群聊驱动）、能力（专才分工+验收官+质量门+记忆进化）、可审计性（task_id 归因+看板留痕）显著优于现有单 Agent；**本轮 0.64.13 补齐的主动性（停滞预警/自动补队）与最终验收门禁（A1-A5）让"无人值守交付"闭环成立**（真实库已见 4 条 ✅ 最终验收通过消息）。
2. **token 效率的真实格局**：实测同一简单任务，群聊模式 59 次调用 / ~199k tokens / 201s，单一 Agent 1 次调用 / 1.1k tokens / 4.4s（≈183× token、46× 耗时）——**但准确性持平（6/6），群聊模式额外买到的是"可验证交付物"（文件+测试+覆盖率证据）与全链路留痕**。开销主因是质量门+验收官的多轮补做循环，属质量体系代价，非 bug。
3. **模型与上下文管理现状**：多模型按 **role 维度**落地（model_configs + 候选链降级），成员级 `model_cfg` 为预留字段未接入执行链；上下文按任务隔离（`_TOOL_TASK` contextvar）+ 爆炸半径聚焦 + 群聊 6 条注入 + 经验加权召回，并发安全、串扰可控。
4. **适用边界**：复杂/工程型/需验证任务 → 元神模式（质量收益 > token 成本）；简单单跳任务 → 单一 Agent 更优（快 46 倍、省 183 倍 token）。

### 4.2 建议（按优先级）

1. **成员级 model_cfg 接入执行链**（P1）：`agent_members.model_cfg` 目前是元数据，执行链按 `model_configs` 角色维度取模型；让"群聊里每个成员真正用不同模型"落地，需把成员级配置并入 `_available_providers` 候选链首位（该字段与降级链机制已就绪，改动面小）。
2. **token 开销显性化**（P1）：实测显示群聊模式结构性多跳；建议在驾驶舱 KPI 增加"任务 token 构成"（调度/执行/验收三段占比），让用户对成本有感知；`cost_visibility_enabled` 已按 task 聚合（6925-6939），前端展示即可。
3. **上下文压缩续优化**（P2）：角色执行上下文仍会随项目成长膨胀（历史 architect max_in 6.7k）；爆炸半径已聚焦，可再引入"任务级上下文快照/增量"（E6 会话归档已铺路）。
4. **简单问答快路径**（P2）：元神已对闲聊只回复不派单；可再评估"单跳直答"开关（小任务直接由元神单上下文完成，不建卡不派单），进一步降低高频小请求开销。
