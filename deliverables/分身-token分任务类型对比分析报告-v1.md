# 分身 vs 其他 Agent：分任务类型的 token 消耗对比分析（v1）

> 2026-08-19 ｜ 基于 SEMVER 0.64.14（token 档位体系上线后）实测 + v6.4 全面评测数据
> 对比对象：**分身**（档位化群聊模式：T0 即时直答 / T1 单角色速办 / T2 团队协作 / T3 长程自治）vs **单一 Agent**（单上下文直答，ChatGPT/Claude/CodeBuddy 类）
> 核心问题：不同任务类型下，两者的 token 消耗**总量**与**速度**是否不同？—— 是，且差异显著分化。

---

## 一、核心结论（你的判断成立）

> **分身的 token 消耗（总量与速度）随任务类型剧烈分化：简单任务已与单一 Agent 拉平（甚至更省），复杂任务仍是质量优先的高开销。不存在一个固定的"几倍"数字——评测报告里的 183×/46× 只是"复杂工程任务"这一格的数字。**

档位体系的本质：**按任务复杂度，选择性支付"质量体系成本"**（调度、验收、交叉验证、补做）。简单任务不付，复杂任务才付。

| 任务类型 | 分身档位 | 分身 总量/耗时 | 单一 Agent 总量/耗时 | 差距（总量/耗时） | 谁更优 |
|---|---|---|---|---|---|
| 即时问答 | T0 | 1 调用 / 536 tok / **0.7s** | 1 调用 / ~0.5k tok / ~1s | **≈1×/≈1×（拉平）** | 持平 |
| 单角色小任务 | T1 | 4 调用 / 9.2k tok / **4.6s** | 1 调用 / 1.1k tok / 4.4s | ≈8× / ≈1× | 单一 token 省，分身得真实交付物 |
| 复杂工程任务 | T2 | 59 调用 / 198.9k tok / 201s | 1 调用 / 1.1k tok / 4.4s | ≈183× / ≈46× | 分身质量+可验证交付物 |
| 长程项目（多任务） | T3 | 总量高但按任务摊薄/并行 | 需人工逐个启动 | 摊薄后 ~3-10× | 分身无人值守+并行+质量门 |

## 二、分析框架：总量 × 速度 × 任务复杂度

```
维度1 总量：完成任务消耗的 token 总和（input+output）
维度2 速度：端到端耗时（用户感知的"快慢"）+ token 消耗速率（tok/s，模型调用侧的"吞吐"）
维度3 任务复杂度：可拆解性（跨角色？多文件？需测试验证？）→ 决定分身走哪个档位
```

**关键洞察**：
1. **总量差距只在"质量成本"上**：分身多花的 token = 调度 prompt + 验收判定 + D8 交叉 + 补做轮 + 每角色独立人格上下文。简单任务不触发这些 → 差距消失。
2. **速度差距在"串行跳数"**：T2 多角色串行（调度→执行→验收→可能补做）天然比单一 Agent 慢；T0/T1 只有 1-2 跳 → 拉平。
3. **"速度"的另一面**：T3 长程项目里，分身能**并行 3 项目** + 无人值守 + 质量门防返工——单看单任务 token 不划算，看"项目级总账"反而高效（返工少、停机少）。

## 三、分任务类型实测明细

### 3.1 即时问答（例："这个项目的目标是什么？介绍一下"）
| 指标 | 分身 T0（0.64.14 实测） | 单一 Agent（同模型估算） |
|---|---|---|
| LLM 调用 | **1 次** | 1 次 |
| input tokens | **536** | ~500 |
| output tokens | 9 | ~300 |
| 端到端耗时 | **0.7s** | ~1s |
| 任务卡/留痕 | 无（不建卡） | 无 |
| 质量保障 | 元神人格+宪法 | 无 |

→ **打平**。档位化前分身同样问题要走完整调度链路（约 3-5k input），档位化后只付 536。**这是本次更新最大的收益点**（高频低价值场景）。

### 3.2 单角色小任务（例："写 hello.py 并保存" / is_prime）
| 指标 | 分身 T1（0.64.14 实测） | 单一 Agent（v6.4 评测实测） |
|---|---|---|
| LLM 调用 | **4 次**（调度1+角色执行3：含写文件/跑命令工具循环） | 1 次 |
| input+output | **9.2k** | 1.1k |
| 端到端耗时 | 4.6s | 4.4s |
| 交付物 | **真实文件落盘 + 执行验证**（hello.py 已写入并运行输出） | 文本回复（代码块） |
| 准确性（is_prime 隐藏6例） | — | 6/6 |

→ 总量 ~8×，但**耗时持平**（工具循环并行快）+ 交付物真实可验证。档位化前同类任务走 T2 完整链路（59 次/198.9k/201s），**现在 T1 把 is_prime 从 198.9k 压到 9.2k（降 21.6×）**。

### 3.3 复杂工程任务（跨角色/多文件/需测试——is_prime 走 T2 完整链路时）
| 指标 | 分身 T2（v6.4 评测实测） | 单一 Agent（同评测） |
|---|---|---|
| LLM 调用 | 59 次（元神3+后端17+测试39） | 1 次 |
| input+output | **198.9k** | 1.1k |
| 端到端耗时 | 201s | 4.4s |
| token 速率 | 989 tok/s | 248 tok/s |
| 交付物 | is_prime.py + test_prime.py + pytest 日志 + **覆盖率 100% 报告** + 9 张看板卡留痕 | 文本回复 |
| 准确性 | 6/6 | 6/6 |

→ 总量 ~183×、耗时 ~46×，但买到的是**可验证交付物 + 全链路留痕 + 质量门防返工**。注：档位化后这类"单角色可完成"的任务会被元神合理降档到 T1（9.2k），**只有真正跨角色的任务才保留 T2 开销**。

### 3.4 长程项目（多任务持续交付，例：一个产品的完整开发）
| 指标 | 分身 T3 | 单一 Agent |
|---|---|---|
| 调度 | 续航调度器（autopilot 15s/并发3）自动拆任务逐卡推进 | 无，需人工逐个下达 |
| token 总量 | 高，但**按任务分档摊薄**（简单卡 T0/T1、复杂卡 T2） | 每任务 1 次调用，总量低 |
| 有效 token 占比 | 高（质量门拦截返工、验收防遗漏） | 低（自产自销，返工靠人工发现） |
| 并行/无人值守 | ✅ 并发 3 + 无人值守 + 终验门禁 | ❌ 必须人在场 |

→ 单看"单任务 token"分身更贵；看"项目总账"（返工率/停机时间/多任务并行）分身效率占优。这是**"速度"的另一层含义**：同样的项目，分身花的时间墙钟更短（晚上也在跑）。

## 四、为什么不同——结构化归因

```
分身 token 构成 = 调度(0.5-1k) + 角色执行(2.5-4.5k/角色×N) + 验收(1-2k/任务)
                 + D8 交叉(2-3k/代码任务) + 补做轮(每轮全重付)
单一 Agent 构成 = 单上下文(1-3k) × 1

档位化的作用 = 按复杂度裁剪上述构成：
  T0 → 只付"调度"的轻量版（536）
  T1 → 调度 + 1 角色执行（9.2k），不付验收/D8/补做
  T2 → 全构成（198.9k），质量优先
  T3 → 全构成但按任务分档摊薄 + 并行
```

**同一任务在两边的"准确性"可以相同（6/6），但交付物性质不同**：分身给"文件+测试+证据链+留痕"，单一给"文本"——token 差价的本质是买"可验证的执行力"。

## 五、选择建议（按场景）

| 场景 | 推荐 | 理由 |
|---|---|---|
| 日常问答/咨询 | 分身 T0 或任意助手 | 已拉平，怎么都行 |
| 小工具/脚本 | **分身 T1** | 总量多 8×但得真实文件，耗时持平 |
| 需要跑测试/覆盖率的工程任务 | **分身 T2** | 质量优先，token 换可验证交付物 |
| 产品级多任务 | **分身 T3** | 无人值守+并行+终验，总账高效 |
| 一次性纯文本生成（写段文案） | 单一 Agent | 无文件/验证需求，没必要付多跳成本 |
